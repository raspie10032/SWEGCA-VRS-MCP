# Replay 맥락을 통한 임시 연결 조회

기존 정확 cue와 직전 연결 ID에 더해, 성공한 Replay의 봉인된 관측에 기록된
`context` 식별자로 임시 VRS의 다른 연결을 찾는 경로를 추가했다.

## 코어 조회 순서

입력의 Déjà vu 키를 계산한 뒤 코어 `familiarity_key`가 다음 우선순위를 적용한다.

1. 임시 VRS의 정확 cue
2. 임시 VRS에 존재하는 직전 Replay 연결
3. 두 경로가 없으면, 직전 Replay와 같은 context를 가진 임시 경험
4. 임시 결과가 없을 때 기존 Main 조회

정확 cue나 직전 연결이 있으면 context 색인을 조회하지 않는다. 코어의 기존 임시
우선 정책을 유지하므로, context로 발견한 임시 경험도 Main보다 우선한다. 이 결과는
조회 후보이며 현재 발언의 진실성·행동 권한·연결 강화 근거가 아니다.

## 생성·보존 경계

- context 키는 선택 원경험의 전체 Replay가 성공하고 주소 검증을 통과한 뒤에만
  저장한다. 부분 읽기, 실패한 Replay, 원문 유사도 또는 모델 발화로 만들지 않는다.
- SessionRuntime은 커밋된 연결의 봉인된 관측에서 context→원경험 참조를 구성한다.
  새 경험도 기존 저장·셔플·코어 검증·catalog 발행 후에 이 색인에 노출한다.
- 색인용 공간은 영속 변경 전에 예약한다. 재시작 시 검증된 연결 이력으로 재구성한다.
- context 후보는 `(연결 ID, 원경험 번호)` 순서를 유지한다. 실시간 기록과 복구가
  같은 순서를 사용한다. 원문·관측을 복제하거나 새로운 증거 표본으로 세지 않는다.
- 위 참조 색인은 **임시 세션**에 적용된다. 아래 Main 맥락 포털은 별도의 Main 소유
  구간 색인을 사용한다. 같은 digest라는 기록된 관계 외의 의미를 추정하지 않는다.

## 검증과 비용

세션 Runtime 검사 515개, 영속 Main 검사 1,076개, MCP 검사 2,213개가 통과했다.
새 사례는 Main의 원경험 Replay 후 다른 임시 연결 두 개로 이어지는 경로, 관계없는
맥락 제외, 정확 cue 우선, 부분/실패 Replay의 키 생성 금지, 조회 중 pread/pwrite 없음,
Replay에 의한 강도 불변, 재시작 후 동일 순서를 검사한다.

추가 context 색인은 메모리를 사용한다. 현재 참조 하나는 64비트 실행 환경에서
32바이트 연결 ID와 8바이트 원경험 번호이며 vector 여유 용량과 context별 트리 노드가
별도로 필요하다. 이는 전체 4GB 운용 완료를 뜻하지 않는다. 조회는 경험 원문을 읽지
않지만 후보를 많이 찾으면 receipt 생성 비용이 증가한다. 지역별 제한·디스크 적재와
실제 앱 입력 지연 검증은 계속 남아 있다.

## Main의 기록된 맥락 포털

MainGraph가 `context → (연결 ID, 원경험 구간)` 색인을 소유한다. 활성 라우터마다
이를 복제하지 않는다. 명시적으로 종료·발행된 세션을 병합할 때 새 봉인 관측으로부터
구간을 준비한다. 같은 연결의 인접한 맥락 구간은 합치며, 원경험이나 검증 표본을
복제하지 않는다. 준비 중 할당 실패는 기존 공개 그래프를 바꾸지 않고, 영속 병합 기록
뒤 확정 단계에서는 준비된 노드를 이동한다.

Main 조회에서 정확 cue가 없고, 성공한 Replay의 context가 **서로 다른 연결**을
가리키면 코어가 context 경로를 선택한다. 연결 하나에만 있는 context는 기존 직전
연결 조회를 대체하지 않는다. 임시 VRS 우선 규칙과 정확 cue 우선 규칙은 유지한다.
후보는 기존 연결 지역 디렉터리를 통해 찾고, 선택 원경험만 Replay한다. 기록된 맥락의
일치는 조회 관계이며 지지·반박·진실·행동 권한의 증거가 아니다.

이 색인은 원본 관측과 검증된 병합 이력에서 재구성된다. 별도 외부 데이터베이스나
포털 판정기를 추가하지 않았다. Main 세대가 바뀌면 오래된 Recall은 기존 규칙으로
거부되며, 라우터를 갱신한 후 새 맥락 구간을 조회한다.

검증: Main 그래프 4,715개(916개 할당 실패 지점 포함), 영속 Main 1,089개,
세션 Runtime 515개, MCP 2,213개 통과. 257개 연결/두 주소 지역의 재시작 후 서로
다른 지역에 있는 두 맥락 연결을 조회·Replay했다. 추가 병합 후 후보가 세 개로
늘어나는 것, 이전 receipt 거부, 원문 읽기 없이 조회, 강도 불변을 확인했다.
코어 familiarity 분기는 CPU 6의 2,000,000회 단독 측정에서 평균 1.132ns/call이었다.
전체 입력→Recall 1ms 달성의 증거는 아니다.

남은 한계: 이 기능은 **기록된 context 관계를 통한 Main 조회**다. 자연어 의미로
맥락을 새로 판별하거나, 동일 원경험을 여러 가설에 공유하는 전체 그래프를 완성한
것은 아니다. context 구간 수에 비례하는 메모리가 추가되며, 디스크 퇴거·적재와
전체 4GB 운용 검증도 남아 있다. 별도 SessionRuntime들을 직접 mount하는 예전
호출 방식은 기존 조회를 유지하고, Main 포털은 실제 PersistentMainGraph 경로에 적용된다.

## 반복 문장 없이 대화를 시작하고 잇기

성공한 Replay가 없으면 서로 다른 자연 입력이 계속 조회 실패하는 누락을 수정했다.
기존 정확 cue/Replay 연결/Main 조회가 모두 비었을 때, 현재 임시 세션의 봉인된
입력 경험을 기록된 session context로 찾는다. 세션 이름 키는 라우터 생성 시 한 번
계산한다. 원문·로그 검색이나 추가 세션 이름 해시는 입력→Recall 앞에 넣지 않는다.

대화 시작 후보는 기존 원경험 헤더의 입력 키 표식(byte 158)이 있는 경험으로
한정한다. 일반 Runtime::receive도 native receive_envelope처럼 계산한 입력 키를
원경험에 보존한다. content/lifecycle retain은 표식을 만들지 않는다. 따라서 세션
시작 알림만으로 대화를 시작하지 않는다. 표식은 원문 체크섬에 포함되며 전체 읽기·
스트림 읽기·재시작 복구가 동일 값을 유지한다. 저장 형식이나 이관 경로는 추가하지
않았다. 표식이 없는 기존 경험을 추측으로 입력 경험으로 바꾸지도 않는다.

약한 session context 시작 경로가 Main의 정확 일치를 가리지 않도록 기존 조회가
모두 비었을 때만 적용한다. 성공한 Replay의 context가 임시 VRS의 여러 연결에
이어져 있으면 기존 familiarity_key의 linked_context 분기로 전체 연결 후보를
찾는다. 직전 연결 하나가 남아 있다는 이유로 계속 그 연결에만 머물지 않는다.
이 연결 확장은 원경험의 지지/반박/기권 상태를 필터링하지 않는다.

다른 문장 세 개의 순차 입력 및 재시작 뒤 다른 문장에서 직전 경험 회상을 확인했다.
조회 중 원문 I/O는 없으며 대조 결과는 근거 부족일 때 계속 기권이다. 데스크톱
프록시 재개 검사도 문장을 바꾼 입력과 첨부를 사용해 이전 입력 경험 주입을 확인했다.
이는 기록된 대화 관계를 잇는 기능이며 자연어 의미 검증/주제 판별/목적 유지력의
완성을 뜻하지 않는다.

## 새 관측 뒤 자동 대조 결과 갱신

선택 원경험과 자동 대조 결과를 가진 호스트가 같은 연결의 새 관측을 기록하면
자동 대조 캐시를 갱신 대상으로 표시한다. 기록 성공 시 해당 관측의 seed/step을
사용한다. 기본 전체 Replay 요청은 기존에 인증해 소유한 원경험을 유지하고
현재 관측의 코어 비교를 다시 수행한다. 충돌일 때만 기존 Re-evidence 경로로
진입하며, 원경험을 다시 선택하거나 읽기 위한 별도 복제를 만들지 않는다.
새 관측이 없으면 갱신한 결과를 재사용한다. 다른 연결의 관측은 이 캐시를
무효화하지 않는다. 원문 변경이나 외부 의미 판정, 권한 부여는 없다.

대조 무효화는 기록 시도 전에 수행해 실패로 세션이 사용 불가능해진 경우에도
과거 캐시를 통해 검증을 우회하지 않게 한다. seed/step은 기록 성공 후에만
갱신한다. 갱신 자체가 실패하면 이전 대조를 성공 응답으로 내보내지 않는다.
명시적 후보 선택과 부분 Replay의 기존 경로는 유지한다.

실제 호스트 회귀 사례: 자동 대조가 insufficient인 입력에 같은 연결의 반박
관측 8개를 추가한 후, 기본 Replay가 동일 원주소에서 contradicts 및
reEvidencePerformed=true를 반환한다. 관측의 최신 step=1과 원경험 수 8,
반복 출력 일치, 잘못된 outcome 요청이 기존 결과를 바꾸지 않음을 검사한다.
일반 자연어의 support/refute 도출 구현을 이 수정으로 달성했다고 주장하지 않는다.

일반 호스트 `retain`도 같은 기록 후 갱신 함수를 사용한다. 성공한 refinement의
연결 ID/seed/step을 사용하므로 다른 연결의 경험은 기존 대조를 바꾸지 않는다.
현재 연결에 미판정 경험을 더 보존한 사례에서 currentOriginalCount는 1→2로
갱신되지만 agreement=insufficient, status=abstain, 재검증 없음, 권한 없음이 유지된다.
불완전한 출처로 기록이 실패해 세션이 unusable이 된 뒤에는 오래된 자동 결과를
내보내지 않고 Replay 오류를 반환하는 것도 실제 프로세스 검사로 확인했다.

명시적 vrs_re_evidence가 자동 선택된 원경험을 성공적으로 대조한 경우, 같은
실행 중 receipt의 기본 Replay도 그 결과를 사용한다. 반환 JSON 구성까지 성공한
뒤에만 대조/재검증/seed/step을 교체하므로 잘못된 요청이 기존 결과를 덮어쓰지
않는다. 원주소와 후보는 유지하며 별도 재선택·원경험 재읽기를 하지 않는다.
이미 영속 저장한 입력 당시 cognition은 과거 기록으로 보존한다. 이 갱신은
실행 중 receipt에 한정되며 명시적 재검증 요청 자체의 재시작 복구 구현은 아니다.

## 대조용 경험 복제 제거

Replay 대조는 Recall 당시 경계 이후의 임시 관측만 사용한다. 이전에는 그 관측들을
새 Connection에 모두 append해 복제한 뒤 평가했다. 이제 evaluate_suffix가 같은
구간을 원본 시퀀스에서 읽고 기존 셔플·admission·그룹 합산·3상 코어를 실행한다.
기존 복제 경로가 하던 관측 유효성 검사는 유지한다. 결과의 표본 번호와 revision은
구간 내부 기준으로 기존 새 Connection 결과와 같으며, 원래 연결에 커밋되지 않는다.
현재 원주소 목록은 같은 구간 순서로 보존한다. 현재 연결이 없는 경우에는 기존
빈 평가를 사용한다. 원문을 읽거나 과거 누적 tally를 판정 입력으로 쓰지 않는다.

300개 관측에서 시작점 0/1/63/127/255/299/300과 seed 1/991의 14가지 조합으로
복제 평가와 전체 refinement_digest 일치를 확인했다. 빈 구간·잘못된 경계 및
원래 강도/revision 불변도 검사했다. 기존 정상 연결의 digest 고정값도 동일하다.
이는 관측 객체 복제를 제거한 것이며, 셔플 표본·집계와 반환 원주소 목록의 선형
메모리까지 없앤 것은 아니다. 전체 4GB 운용이나 자연어 의미 판단 완결은 아니다.

## 같은 이름의 독립 세션 구분

자연 입력의 대화 맥락 키를 `SWEGCA input session v2` 도메인과 고정 32바이트
SessionStore 소유자 ID, 세션 이름으로 구성한다. native 세션의 소유자 ID에는
기존 provider/instance/session 식별이 결합되어 있다. 기록 시점과 라우터 생성 시점에
같은 함수를 사용하며 매 Recall 앞에 별도 세션 해시를 추가하지 않는다.

이전의 이름만 사용한 키는 다른 소유자가 같은 이름을 사용하면 Main 맥락 포털에서
합쳐졌다. 같은 이름의 A/B 세션을 각각 종료·병합한 뒤 재시작하고 A 경험을 Replay한
회귀 사례에서, 새 대화 키는 A의 두 원경험만 찾는다. B 경험도 정확 cue로 Main에서
조회할 수 있다. 원문 일치에 의한 공유 조회나 명시적으로 기록된 context 관계를
금지하는 변경이 아니며, 이름 충돌을 대화 관계로 만드는 경로만 수정한다.

이 규칙은 새로 기록하는 자연 입력의 맥락 키에 적용된다. 이미 봉인된 기존
관측의 context와 checksum은 그대로 기록된 값이며 다시 작성하지 않는다.
이전 키로 작성된 데이터의 맥락 혼합이 소급해서 해소됐다고 주장하지 않는다.
