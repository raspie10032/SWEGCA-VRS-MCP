# Main 정확 조회 색인의 연속 구간 표현

기존 색인은 `(입력 cue, 연결 identity, 원경험 index)`마다 별도 트리 노드를 보관했다.
같은 연결에서 같은 cue를 가진 원경험 index가 연속될 때는 `[begin,end)`로 보관한다.
원경험·봉인된 관측·연결·강도·셔플 순서·판정은 변경하지 않는다. 의미적 region이나
portal을 새로 정의한 것도 아니다. 정확 조회 색인의 물리 표현 변경이다.

정렬은 여전히 연결 identity 다음 원경험 index 순서다. 불연속한 같은 cue, 다른 cue,
다른 연결을 하나의 구간으로 합치지 않는다. 원경험은 모두 개별 후보로 조회된다.

증분 발행은 이전과 같이 새 노드를 전부 준비한 뒤 수행한다. 기존 구간과 이어지는
새 구간은 end만 갱신하고 준비 노드를 해제한다. 나머지는 할당 없는 node transfer로
옮긴다. 준비 중 할당 실패는 기존 색인·indexed generation을 변경하지 않는다.

검사에서는 같은 연결의 같은 cue가 8개에서 24개로 늘 때 상주 색인 추가 할당이
0바이트임을 확인했다. 여러 연결의 A/B/A/A/B 입력 배열로 불연속 구간을 검사하고,
증분 색인과 전체 재구축 모두를 실제 Main 경험의 cue/index/주소 순서와 대조한다.
4개 준비 할당 지점의 실패·재시도와 옛 receipt 보존 검사도 통과한다.

한계: cue가 매번 다르거나 번갈아 나타나면 구간 수는 경험 수에 비례한다. 단일 구간
노드는 끝 index도 보관하므로 고립된 경험에서 기존보다 더 작다고 주장하지 않는다.
Main의 봉인된 경험과 연결은 여전히 상주하며, 불연속 정확 Recall 결과는 후보마다 pin을
만든다. 이 변경은 임의 크기 그래프의 4GB 운용이나 region/portal 완성의 증거가 아니다.

## 정확 Recall 결과의 단일 구간 보존

정확 cue의 Main 후보가 하나의 연속 구간이면, Recall 결과도 그 구간을 덮는 세그먼트의
공유 소유권만 보관한다. 후보를 꺼낼 때 원래 index와 봉인된 주소를 조립한다.
ExperienceSequence::Snapshot은 begin/end를 검사하고 해당 세그먼트 범위만 핀한다.
원 소유자 해제나 뒤의 append 이후에도 당시 범위만 조회되며, 이동된 이전 객체는 비어 있다.

여러 불연속 구간이면 기존 후보별 참조를 사용한다. 희소한 후보마다 큰 context나 전체
세그먼트 디렉터리를 복제하는 역효과를 피하기 위한 저장 표현 선택이며 후보의 의미·순서나
SWEGCA 판단을 바꾸지 않는다. 단일 구간의 작은 선택도 물리 세그먼트 한 개 전체를 유지할
수 있고, 구간 양끝보다 바깥에 있는 같은 세그먼트의 데이터도 함께 살아 있다.

continuation도 같은 범위 스냅샷을 사용한다. 구조에 시작점과 첫 세그먼트 번호가 추가되어
기존 continuation/후보별 context의 고정 크기는 증가한다. 따라서 모든 입력 형태에서
메모리가 줄었다고 주장하지 않는다. 정확 조회의 큰 연속 결과를 후보마다 전개하는 비용을
줄였으며, 전체 연결·봉인된 경험 상주 및 임의 크기 그래프의 4GB 운용 문제는 남아 있다.

실측: Main 정확 조회 8개 후보의 receipt는 264 추적 바이트를 사용했다.
세그먼트 경계 7/8, 23/24, 55/56, 119/120, 247/248, 503/504, 1015/1016 및
빈 범위·전체 끝·잘못된 범위·move·owner 해제 후 보존을 검사했다.
