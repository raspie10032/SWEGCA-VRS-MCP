# 관측 복구의 고정 버퍼 검증

PersistentConnection의 복구와 기록 후 관측 검증은 이제 전체 StoredExperience 버퍼를
만들지 않는다. SessionStore의 기존 1블록 reader cursor에서 원경험을 읽되, 고정 64KiB
버퍼로 전체 기록을 검증하고 176바이트 관측 헤더와 조회 키 해시만 유지한다.

## 동일한 검증 경계

1. 블록 소유, 주소·길이·용량·읽기 한도와 기록 framing을 확인한다.
2. session/source/외부 media/content의 모든 바이트를 순서대로 읽고 SHA-256에 반영한다.
3. 관측 헤더의 magic, reserved 값, 만료 flag, 내부 media/payload 길이를 검사한다.
4. 내부 media와 원문 전체를 기존 input_cue와 동일한 해시에 스트리밍한다. domain과
   little-endian media 길이 prefix는 input_cue_prefix로 공유하며 판정식은 추가하지 않았다.
5. 기록 trailer·완료 표시·실제 해시·요청 주소의 해시가 일치해야 visitor가 반환한다.
6. 기존 SWEGCA admit_observation을 거쳐야 ExperienceEvidence를 생성해 연결에 넣는다.

외부로 미검증 chunk를 내보내는 API가 아니다. private visitor의 소비자는 관측 디코더
하나이며 전체 검증 전에 봉인된 관측이나 원경험을 반환하지 않는다. 읽기 실패·끝부분 손상·
형식 오류 시 결과 없이 실패한다. 정상 수락 경로의 체크섬·출처·불확실성·코어 판정을
생략하지 않는다. 일반 전체 읽기와 스트리밍 읽기는 같은 관측 필드 디코더와 코어 검사를 쓴다.

기존 메타데이터/저널 읽기는 크기가 제한된 StoredExperience를 그대로 사용한다. 블록
reader 재사용, 원경험 주소, 디스크 형식, 규칙, 셔플 순서와 복구 중 결과 해시 검사는 유지한다.
저장소의 TransferBudget도 모든 pread에 적용한다.

## 검증

- 2MiB 원문 및 1/65,359/65,360/65,536/65,537바이트 media에서 전체 읽기와 스트리밍
  읽기의 주소·cue·관측값이 동일한지 검사한다. 첫 chunk 경계 안팎과 빈 원문을 포함한다.
- 실제 pread 최대 요청이 65,536바이트 이하인지 계수한다.
- 관측 헤더 형식 오류, 읽기 한도 초과, 중간 EIO, 원문 끝부분 손상을 거부하는지 확인한다.
- 64KiB의 추적 할당 예산으로 2MiB 원경험을 기록 후 검증하고 재개방·연결 복구한다.
  원문 fixture는 호출자 소유이며, 복구 단계에는 남아 있지 않는다.
- 고정 버퍼는 스택에 있으므로 PMR 할당 계수에는 포함되지 않는다. 전체 프로세스 메모리
  제한과 구분한다. 각 동시 reader가 이 스택 공간을 별도로 사용한다.

결과: 블록 검사 네이티브/UBSan trap 각각 202개, 연결 15,028개, 영속 연결 복구 77개,
실제 stdio 서버 1,184개 통과. CPU 6·7, 최대 2개 컴파일 작업으로 진행했다.

## 남은 범위

선택 Replay가 원문을 호출자에게 반환하는 API는 여전히 전체 버퍼를 사용한다. 위 64KiB
예산에서는 2MiB 전체 Replay가 bad_alloc으로 거부되는 것도 검사한다. 따라서 이것은
“2MiB 원경험 복구의 대형 임시 버퍼 제거”이며, 전체 Replay 스트리밍이나 4GB/500GB 규모
시스템의 완성 증거가 아니다. 원문 전체의 I/O와 해시는 계속 수행하므로 I/O량 감소 또는
복구 시간의 상한을 이 변경만으로 주장하지 않는다.
