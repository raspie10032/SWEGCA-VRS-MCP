# 단일 경험 연결의 초기 예약 축소

기존 ExperienceSequence의 첫 세그먼트는 경험 8개를 예약했다. 서로 다른 자연 입력은
각각 새 연결에 들어가므로 경험 1개인 연결마다 빈 7개분의 봉인된 값 공간을 보관했다.
초기 용량을 1로 바꾸고 1,2,4,8,...,128 이후에는 기존처럼 256개 세그먼트를 사용한다.
임의 index 접근은 bit_width와 정수 연산으로 계산한다. 선형 탐색은 추가하지 않는다.
Snapshot·pin·일반 접근은 같은 주소 계산 함수를 사용한다.

원경험, 관측값, 실제 셔플, 원본 집계, 3상 판정, 강도, 원경험 순서 및 저장 형식은
변경하지 않는다. 커지는 연결은 초기 단계의 세그먼트/디렉터리 할당 횟수가 늘어난다.
따라서 모든 분포에서 더 빠르거나 더 적은 메모리를 쓴다고 주장하지 않는다.

## 동일 실제 경로 비교

기준 f6e3e48, 변경 후 이 문서와 함께 커밋한 코드. 동일 머신, CPU 6·7,
GCC -O3, worker 2, 256MiB PMR, 128바이트의 서로 다른 자연 입력 8,192개.
Runtime receive → 종료 → Main 병합 → Main 조회/선택 Replay → 재시작 복구를 실행했다.
재시작은 OS 캐시를 비우는 물리 cold-cache 실험이 아니다. 컴파일 완료 뒤 측정했다.

실행: `taskset -c 6,7 build/recall-scale-bench 8192 distinct 2`
원자료: benchmarks/results/recall-singleton-{before,after}-8192.jsonl

| 단계 | 전 추적 bytes | 후 추적 bytes | 감소 |
| --- | ---: | ---: | ---: |
| 기록 후 | 27,985,184 | 10,552,608 | 62.29% |
| Main 병합 후 | 26,936,360 | 9,503,784 | 64.72% |
| Main 색인/활성 세션 | 30,738,376 | 13,305,800 | 56.71% |
| 재시작 복구 후 | 30,738,376 | 13,305,800 | 56.71% |

저장 bytes는 양쪽 모두 17,892,515. 프로세스 최대 RSS는 이번 단일 실행 쌍에서
72,352 → 29,940 KiB였다. PMR 감소와 RSS 감소를 같은 수치로 취급하지 않는다.
측정한 각 조회는 디스크 읽기/쓰기 없이 실제 Recall 경계에 진입했으며 후보 수와
선택 원주소를 확인했다. 이 결과는 과거 동시 작업의 1ms 초과 사례를 해소한 증거가
아니며 실제 앱 연결이나 임의 입력 길이·임의 그래프 크기의 지연 보장도 아니다.

새 세그먼트 경계의 실패 주입, 공유 prefix/꼬리 복제, 범위 snapshot, owner 해제,
기존 고정 refinement digest 검사까지 포함한다. 이 물리 예약 축소는 의미적 그래프
분할/portal을 구현한 것이 아니며, 상주 경험 수에 비례하는 구조는 아직 남아 있다.
