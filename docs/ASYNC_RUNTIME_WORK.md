# Runtime 백그라운드 병합 준비

`Runtime::schedule_work(seed, step)`은 현재 종료·발행된 원천 목록을 고정하고 내부 워커를
시작한다. 각 원천의 필요한 복구 및 전체 실제 경험 셔플·SWEGCA 검증은 워커에서 수행한다.
Main의 이미 발행된 그래프는 준비 동안 그대로 읽을 수 있다. 활성 임시 세션은 원천 목록에
들어가지 않으며, 예약 이후 종료한 세션은 다음 예약에서 처리한다.

`poll_work()`는 준비 중이면 nullopt를 돌려준다. 준비가 끝났으면 워커를 join하고 Main
소유자에서 영속 기록·발행 및 현재 조회 인덱스 갱신을 한다. 다음 원천이 있으면 워커를
시작하고 nullopt, 전체 목록이 끝났으면 실제 병합 수를 반환한다. 빈 원천 때문에 이후의
원천을 처리하지 못하는 일이 없도록 목록 위치를 진행한다. 빈 원천 자체의 영속 Main
표시는 기존처럼 발행하지 않으므로 이후 예약에서 다시 무변경으로 확인될 수 있다.

## 소유권과 실패

- public Runtime 호출은 여전히 소유자 한 스레드에서 직렬로 실행한다. 임의의 외부
  스레드에서 start/end/receive/poll을 동시에 호출하는 API가 아니다.
- 내부 워커는 선택된 종료 원천 하나의 캐시를 전용으로 사용한다. 준비 중 플래그는
  소유자만 변경하며, 완료 join 전에 원천 캐시를 읽거나 해제하지 않는다.
- 다른 세션의 시작·기록·종료는 가능하다. 캐시 회수는 작업 중 원천과 활성 세션을 건너뛴다.
- 작업 중 기존 동기 `work` 또는 중복 `schedule_work`는 거부한다. Main 쓰기가 준비의
  읽기와 경쟁하거나 다른 원천의 공개 노드를 바꾸지 않도록 한다.
- 스레드 생성/복구/준비 실패는 소유자에게 전달하고 캐시 점유를 해제한다. 종료 원천의
  영속 발행 표시는 남아 재시도 가능하다. 이미 완료한 앞선 원천의 병합은 되돌리지 않는다.
- 영속 발행 실패의 reopen 규칙은 기존과 같다. 준비 실패와 영속 쓰기 실패를 혼동하지 않는다.
- Runtime 소멸 시 워커를 join하고 미발행 준비 결과를 버린다. 소멸 자체로 세션을
  종료하거나 Main에 병합하지 않는다. MemoryBudget과 upstream은 Runtime보다 오래 살고
  upstream은 동시 할당·해제를 지원해야 한다.

## 입력 경로와 범위

`input`, `receive`, `retain`, `end_session`은 작업을 예약하거나 기다리거나 발행하지 않는다.
호스트는 작업 예약·완료 확인을 입력 처리 바깥에서 수행한다. 종료 원천 발견과 저장소 열기는
예약 호출에서 수행하며, 준비가 완료된 poll의 영속 기록·인덱스 갱신은 아직 동기 실행이다.
따라서 poll 호출 전체의 지연이 상수이거나 1ms 미만이라는 보장은 없다.

stdio 호스트는 `swegca/work/start`로 예약하고 `swegca/work/poll`로 완료 결과를 발행할 수
있다. 요청 처리 자체는 소유자 스레드에서 직렬이다. 새 API를 실제 클라이언트 호스트의
스케줄러에 연결해야 한다. 이 구현을 실제 Codex 입력 훅 또는 세션 전체 자동 수집 완료로
표현하지 않는다. 새 판정 로직이나 외부 분류기를 추가하지 않았으며 Main 준비는
[기존 prepare/commit 계약](MAIN_PREPARATION.md)을 따른다.

검증: async-runtime 네이티브 및 UBSan trap 각각 80개, 기존 Runtime 128개, Main 원천
관리 32개 통과. 워커를 실제 할당 지점에서 멈춰 입력/선택 Replay 및 세션 교체를 확인하고,
스레드 생성 실패·워커 메모리 실패의 재시도와 소멸 시 미발행을 검사했다. ThreadSanitizer로
데이터 경쟁을 검증한 결과는 아니며 실서비스 입력 지연 수치도 이 검사로 주장하지 않는다.
