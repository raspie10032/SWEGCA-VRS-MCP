# Runtime 백그라운드 병합 준비

`Runtime::schedule_work(seed, step)`은 현재 종료·발행된 원천으로 대기열을 만들고 내부
워커를 시작한다. 각 원천의 필요한 복구 및 전체 실제 경험 셔플·SWEGCA 검증은 워커에서 수행한다.
Main의 이미 발행된 그래프는 준비 동안 그대로 읽을 수 있다. 활성 임시 세션은 원천 목록에
들어가지 않는다. 작업 묶음이 유지되는 동안 명시적으로 종료·발행된 세션은 같은
대기열 뒤에 추가되어 다음 예약 없이 처리된다. 추가 원천에도 예약 시의 seed/step을
그대로 사용하며 시각이나 새 난수로 판정 조건을 바꾸지 않는다.

`poll_work()`는 준비 중이면 nullopt를 돌려준다. 준비가 끝났으면 워커를 join하고 Main
소유자에서 영속 기록·발행 및 현재 조회 인덱스 갱신을 한다. 다음 원천이 있으면 워커를
시작하고 nullopt, 전체 목록이 끝났으면 실제 병합 수를 반환한다. 빈 원천 때문에 이후의
원천을 처리하지 못하는 일이 없도록 목록 위치를 진행한다. 빈 원천 자체의 영속 Main
표시는 기존처럼 발행하지 않으므로 이후 예약에서 다시 무변경으로 확인될 수 있다.

## 소유권과 실패

- public Runtime 호출은 여전히 소유자 한 스레드에서 직렬로 실행한다. 임의의 외부
  스레드에서 start/end/receive/poll을 동시에 호출하는 API가 아니다.
- 내부 워커는 선택된 종료 원천 하나의 캐시를 전용으로 사용한다. 준비 중 플래그는
  소유자만 변경하며, 완료 join 전에 원천 캐시를 읽거나 해제하지 않는다.
- 다른 세션의 시작·기록·종료는 가능하다. 캐시 회수는 작업 중 원천과 활성 세션을 건너뛴다.
- 작업 중 기존 동기 `work` 또는 중복 `schedule_work`는 거부한다. Main 쓰기가 준비의
  읽기와 경쟁하거나 다른 원천의 공개 노드를 바꾸지 않도록 한다.
- 스레드 생성/복구/준비 실패는 소유자에게 전달하고 캐시 점유를 해제한다. 종료 원천의
  영속 발행 표시는 남아 재시도 가능하다. 이미 완료한 앞선 원천의 병합은 되돌리지 않는다.
- 영속 발행 실패의 reopen 규칙은 기존과 같다. 준비 실패와 영속 쓰기 실패를 혼동하지 않는다.
- Runtime 소멸 시 워커를 join하고 미발행 준비 결과를 버린다. 소멸 자체로 세션을
  종료하거나 Main에 병합하지 않는다. MemoryBudget과 upstream은 Runtime보다 오래 살고
  upstream은 동시 할당·해제를 지원해야 한다.

## 입력 경로와 범위

`input`, `receive`, `retain`은 작업을 예약하거나 기다리거나 발행하지 않는다.
`end_session`은 명시적 종료 원천을 영속 발행하고, 진행 중인 작업이 있으면 대기열에
그 ID를 추가한다. 워커를 시작·대기하거나 Main 그래프를 갱신하지 않는다.
호스트는 최초 작업 예약·완료 확인을 입력 처리 바깥에서 수행한다. 종료 원천 발견과 저장소 열기는
예약 호출에서 수행하며, 준비가 완료된 poll의 영속 기록·인덱스 갱신은 아직 동기 실행이다.
따라서 poll 호출 전체의 지연이 상수이거나 1ms 미만이라는 보장은 없다.

stdio 호스트는 `swegca/work/start`로 예약하고 `swegca/work/poll`로 완료 결과를 발행할 수
있다. 요청 처리 자체는 소유자 스레드에서 직렬이다. 아래 automaticWork 설정을 사용하면
stdio 호스트가 예약·완료 처리를 자동 수행한다. 실제 데스크톱 설치와 사용자 종료 조작의
연결은 별도이며, 이 구현을 세션 전체 자동 수집 완료로 표현하지 않는다. 새 판정 로직이나 외부 분류기를 추가하지 않았으며 Main 준비는
[기존 prepare/commit 계약](MAIN_PREPARATION.md)을 따른다.

검증: async-runtime 네이티브 및 UBSan trap 각각 80개, 기존 Runtime 128개, Main 원천
관리 32개 통과. 워커를 실제 할당 지점에서 멈춰 입력/선택 Replay 및 세션 교체를 확인하고,
스레드 생성 실패·워커 메모리 실패의 재시도와 소멸 시 미발행을 검사했다. ThreadSanitizer로
데이터 경쟁을 검증한 결과는 아니며 실서비스 입력 지연 수치도 이 검사로 주장하지 않는다.


## 진행 중 추가 종료와 대기열 복구

대기열은 Runtime 소유자만 접근한다. 워커는 현재 지정된 원천과 고정 seed/step만
사용하므로 소유자의 ID 벡터 확장과 경쟁하지 않는다. 용량은 기하급수적으로 늘려
반복 종료마다 전체 대기열을 재할당하지 않는다. 필요한 용량은 세션 종료 전에
MemoryBudget으로 확보한다. 이 확보에 실패하면 세션은 활성·사용 가능 상태를
유지한다. 종료·원천 발행에 성공한 뒤의 삽입은 추가 할당 없이 수행한다.
기존 SWEGCA main_session_readable 판정을 통과한 원천만 대기열에 들어간다.

추가 종료 때문에 이미 처리한 경험을 재탐색하거나 준비 중인 원천을 교체하지 않는다.
Main 공개는 기존 poll_work의 준비 결과 commit으로만 실행한다. 작업 묶음이 없는
경우 종료 원천은 영속 대기 상태로 남으며, 새 예약이 필요하다. 프로세스가 끝나면
메모리 대기열을 버리지만 종료 원천의 영속 발행은 남아 다음 예약에서 발견된다.

검증: async-runtime 91개, 실제 호스트 프로세스 2,918개 통과. 워커를 실제 할당
지점에서 멈춘 동안 두 번째 세션을 종료하여 같은 작업에서 두 원천이 처리되는지,
새로 시작한 활성 세션이 Main에 들어가지 않는지 검사했다. 대기열 확장의 소유자
메모리 실패 후 세션 상태 보존·재시도, 준비/추가 대기 상태에서 소멸 후 재시작하여
두 원천을 모두 복구하는 경로도 확인했다. 아래 stdio 자동 처리 구현이 추가됐으며,
실제 앱의 설치·종료 조작 연결은 남아 있다.


## stdio 호스트 자동 예약·완료 처리

호스트 설정에 다음을 추가하면 초기화가 끝난 뒤 유휴 시 기존 종료·발행 원천을
예약하고, 명시적 swegca/end 성공 후에도 같은 방식으로 예약·poll한다.

```json
"automaticWork": {"seed": "7", "step": "0"}
```

seed/step은 호스트 소유자가 정하는 기존 셔플·검증 인자다. 벽시계로 변경하거나
다른 판정식을 사용하지 않는다. 이 설정을 생략하면 기존 명시적 work/start,
work/poll 방식이며 기본 프레임 읽기에 poll 호출을 추가하지 않는다.

자동 모드에서는 읽기 버퍼나 FD에 이미 도착한 입력을 먼저 처리한다. 부분 프레임을
읽는 중에도 Main 처리를 끼워 넣지 않는다. 입력이 없고 작업이 진행 중일 때만
최대 10ms 간격으로 준비 완료를 확인한다. 작업이 없으면 차단 읽기로 돌아가며,
EOF·idle·turn 종료를 세션 종료 신호로 해석하지 않는다. 이 방식은 진행 중인
동기 commit 도중 새 입력이 도착하는 지연이나 연속 입력에 의한 작업 지연을
해결하지 않는다. 전체 입력→Recall 1ms 보장은 여전히 미달성이다.

자동 준비/commit 실패는 입력 프레임 오류 응답으로 바꾸지 않는다. 호스트는 실패를
stderr로 보고하고 종료 코드 2로 멈춘다. 종료·발행 원천의 영속 대기 상태는 남아
문제를 해소한 다음 실행에서 복구한다. 자동 반복 실패 루프나 임의 재검증은 없다.

검증: 프레임 검사 35개, 실제 프로세스 검사 3,092개 통과. work/start·work/poll
요청 없이 종료 뒤 병합, 재시작 자동 복구, 활성 세션 및 EOF의 비종료, 준비된 입력과
부분 프레임 우선 처리, 저장 한도 소진 시 올바른 실패 종료와 한도 복구 후 재처리를
확인했다. 실사용 앱이나 모델을 실행한 검사가 아니다.
